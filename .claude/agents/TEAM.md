# ZONE Game Team - Orchestration Plan

The six ZONE agents form a game studio, not a pile of coders: one voice owns WHY (is it fun, does it retain), two own the SERVER TRUTH (the numbers and the plumbing), two own what the PLAYER SEES, and one owns HOW IT LOOKS. The organizing law that makes them cohere is ZONE's own design law - server-authoritative always, Torn-simple UI with AAA original cyber-noir art, bilingual AR-RTL + EN by construction, verify every change live in the browser and against engine tests. Map that law onto the roster and the division is clean: the Game Design Director is the studio head and single GDD owner; the Game Architect and the Game Systems & Economy Designer are the twin owners of authoritative state (Architect = the engine, schema, /api/v1 contract, anti-cheat enforcement; Systems = the formulas, curves, economy config, simulations); the Frontend/UI Engineer and the Map & Level Designer are the twin presenters (Frontend = the custom JS template engine and every panel; Map = the Mapbox canvas, the MapGenie-style location sidebar, districts, travel, territory); the Character & Art Designer feeds original assets and the style bible to both presenters. The build always flows Design -> Truth -> Presentation -> Live Verify, and nothing is "done" until it clears its verification gate. Tech-lead (this session) is the synthesizer and traffic controller: it decomposes work, decides solo-vs-parallel, prevents write-collisions on shared files, and enforces the gates between phases.

## Collaboration model

PIPELINE ORDER (the default flow for any new feature): (1) DESIGN - Game Design Director restates the goal, names the loop it serves (core/meta/social), reads live engine + GDD, and writes the feature spec: player flow, data-model touchpoints, server-authoritative rules, AR/EN copy notes, acceptance criteria, and the balance dials. Output is the contract everyone else builds against. (2) TRUTH (runs as a parallel pair off the spec) - Game Systems & Economy Designer derives the formulas, numbers tables, and runs the simulation (grind time, payout/hr, inflation delta, anti-exploit list); Game Architect designs the module boundary, schema + migration, /api/v1 endpoint signatures, and the server-side validation/anti-cheat. They converge: Systems produces the values, Architect owns where they live (config tables) and how they are enforced. (3) SERVER BUILD - Architect implements the endpoint + config against real files; Systems tunes the values into that config. Gate A must pass here. (4) PRESENTATION (parallel pair) - Frontend/UI Engineer builds the panels/components consuming /api/v1 (client is a presenter only, never mutates authoritative state); Map & Level Designer builds anything on the map canvas or location sidebar. Both pull original assets from Art. (5) ART feeds in parallel throughout - Character & Art Designer locks the style bible once, then produces icons/markers/portraits on demand and runs the anti-AI-tell critique pass. (6) LIVE VERIFY - Gate B.

OWNERSHIP BOUNDARIES (how overlaps are resolved, decisive):
- Economy (Director vs Systems): Director owns intent + retention rationale + the targets ("crimes should stay worth grinding to day 7"); Systems owns the actual formulas, tables, and sims that make those targets hold. Director never ships a raw number; Systems never sets the design goal.
- Config vs plumbing (Systems vs Architect): Systems decides the values and curves; Architect owns the config-table schema, the endpoint that serves them, and the server-clock/rate-limit enforcement. If a tuning change needs a new column or a new validation, that is Architect's edit, made off Systems' spec.
- Front-end split (Frontend vs Map): if it is rendered on the Mapbox canvas OR in the categorized location sidebar (POIs, categories, counts, found-tracking, filters, quicksearch, travel/territory controls), it is Map's. Everything else the player sees - stat bars, crimes panel, market, actions, auth screens - is Frontend's. Both edit the single-file JS front-end, which is the #1 contention hotspot: the tech-lead NEVER dispatches Map and Frontend to write in the same turn, and assigns each a clear region.
- API boundary (Architect vs Frontend/Map): Architect owns the /api/v1 contract shape (i18n keys, error shapes, pagination); Frontend/Map consume it exactly and reconcile optimistic UI against it.
- Art vs presenters: Art creates and specs the asset (size, format, palette hex, motif, safe-crop) and proves the look in one render; Frontend/Map place it in context and verify it renders on dark, at real size, in RTL and LTR. Art never invents game state; presenters never invent art.

THE SHARED LAW ALL SIX HONOR: server-authoritative (Systems+Architect own truth, Frontend+Map are presenters, Director specs the rules, Art is presentation-only); bilingual AR/EN in every string, number format, and layout; Torn-dense/utilitarian UI with AAA cyber-noir/cyan original art; and no "done" without live proof.

## Orchestration (how to run them from Claude Code)

RUN THEM VIA THE Agent TOOL FROM CLAUDE CODE, tech-lead as orchestrator. Three dispatch modes:

1) SOLO Agent CALL - for scoped, single-owner work with no upstream dependency: "Frontend: fix the RTL count/checkmark overlap on /map sidebar." One agent, one narrow job, its own verification gate. This is the common case; use it liberally.

2) PARALLEL FAN-OUT (multiple Agent calls in ONE message, or aura-workflow run in parallel mode) - only for work that touches DISJOINT files. Legit parallel sets: Art generating the marker icon set WHILE Systems runs the economy sim WHILE Architect drafts a schema - three different file trees, zero collision. NEVER parallelize Frontend + Map (both write the single-file JS front-end) or Systems + Architect editing the same config in the same turn; serialize those.

3) PIPELINE (sequential, each output feeds the next; aura-workflow pipeline mode or chained Agent calls) - for a dependency chain: Director spec -> Systems numbers + Architect design -> Architect/Systems server build -> Frontend/Map UI -> verify. Pass FILE PATHS between stages, never pasted file contents (subagent prompts self-contained, <=400 words - Rules #14/#20). Every subagent prompt names: the exact module/route/file, whether it touches authoritative state, the URL to verify on, and AR+EN scope.

MODEL-TIER DISCIPLINE (cost): the four opus agents (Director, Systems, Architect, Art) are judgment/design tiers - run their DESIGN passes first and once; the two sonnet agents (Frontend, Map) are the high-volume build+verify loop - hand them the finished spec so opus reasoning is not burned on iterative UI edits. Escalate a sonnet agent to an opus-level design pass only for a full district-system or front-end architecture decision.

TWO VERIFICATION GATES, HARD STOPS between phases:
- GATE A (engine): Architect/Systems must show PHPUnit green AND the live /api/v1 response returning the tuned values (chrome-devtools list_network_requests / get_network_request). Front-end build does NOT start against an endpoint until Gate A is green.
- GATE B (browser): Frontend/Map/Art must show the change rendering live via chrome-devtools - screenshot at 360px and 1440px, toggled dir=rtl AND dir=ltr, console clean, and for non-trivial work a Lighthouse/a11y pass. Art additionally runs its anti-AI-tell critique before Gate B.
No agent may report "done"/"fixed"/"works" without pasting its gate evidence; if it cannot verify, it says so and why (Rule V1).

TECH-LEAD DUTIES each cycle: (a) hold the write-lock on the single-file JS front-end - serialize Frontend/Map; (b) confirm scope in the first sentence (full-app default per Scope Discipline); (c) enforce the gates; (d) route the Director's spec as the single source of truth so no two agents design the same mechanic twice; (e) stop irreversible outbound (a Vercel production deploy is an Approval Gate - stage it, show it, let Weni press it).

## First missions
- ENGINE HARDENING (blocking, run FIRST) - Game Architect: the ZONE engine is in REQUEST CHANGES with 3 open P0s. Audit them, then sweep every state-changing endpoint (money transfer, gym-train, crime, combat) for client-trust vulnerabilities - find each place a client value is trusted, make it server-authoritative with server-clock cooldowns and rate limits, add PHPUnit coverage, and clear Gate A (tests green + live /api/v1 response). This unblocks everything downstream.
- RETENTION SPEC (source of the pipeline) - Game Design Director: diagnose where the meta loop stops giving reasons to return (read engine/modules + GDD + live economy), respec it with a numbers table and D1/D7/D30 retention rationale, and write the feature spec (player flow, server-authoritative rules, AR/EN copy, acceptance criteria, balance dials) that missions 3 and 7 implement. Deliver the GDD entry, not a UI order.
- ECONOMY BALANCE - Game Systems & Economy Designer: audit every faucet and sink across crimes/jobs/market, model the money supply, and design the crime success curve (e.g. ~30% at L1 climbing to ~85% at L50 off Dexterity vs Defense) with anti-farm rate limits. Simulate grind time and inflation delta, then edit the server-side config and verify the live API returns the tuned values (Gate A). Spec against the Director's retention targets from mission 2.
- STYLE BIBLE + MAP ASSETS - Character & Art Designer: lock the ZONE style bible first (cyan-on-dark palette with hex, shape motif, anti-AI-tell rules) and write it to a style-guide file with one proof render. Then produce the original marker/POI icon set the Map needs (consistent grid, reads at icon size on the dark map, mirrors for RTL), run the anti-AI-tell critique pass, and report absolute paths + a one-line spec per asset. Runs in parallel with missions 1-3 (disjoint files).
- MAP POLISH - Map & Level Designer: on /map, add MapGenie-style per-POI found/unfound tracking with per-category X/Y counts persisted SERVER-SIDE via /api/v1 (coordinate the endpoint with the Architect - client renders only), and fix quicksearch so it matches both Arabic and English location names. Consume the icon set from mission 4. Keep the sidebar Torn-simple; verify live in AR and EN with the console clean (Gate B).
- FRONTEND ELEVATION - Frontend/UI Engineer: elevate a core panel (crimes panel or the player stat bar built with sc-for over player state) to the cyber-noir/cyan identity while keeping Torn-dense row spacing, using logical properties for true RTL. Add optimistic-then-reconcile UI on /api/v1 action buttons so the client stays non-authoritative. Verify at 360px and 1440px in AR and EN, no console errors, plus a Lighthouse/a11y pass (Gate B). Serialized against mission 5 on the single-file front-end.
- VERTICAL-SLICE PROVE-OUT (full pipeline dry run) - all six in sequence: ship one complete feature (faction war or a new crime chain) end to end - Director spec -> Systems numbers + Architect schema/endpoint/anti-cheat -> server build + Gate A -> Frontend panels + Map territory UI consuming Art assets -> Gate B in AR+EN. This validates the hand-off model, the gates, and the write-lock discipline on one real feature before scaling to parallel feature teams.
- ECONOMY-CONFIG PLUMBING (paired follow-on to mission 3) - Game Architect off Systems' spec: if the new curves need a config-table column, migration, or a new validation path, Architect owns that edit (SQLite-test compatible, bilingual result keys, indexed for scale), keeping tuning values in Systems' hands and enforcement in the server. Ships behind Gate A.

## Risks
- Single-file JS front-end is a write-collision hotspot: Frontend and Map both edit it. Mitigation - tech-lead never dispatches both to write in the same turn; assign Map the map-route region and Frontend everything else, serialize their commits.
- Economy double-ownership (Director vs Systems) can produce two conflicting number sets. Mitigation - Director ships intent + targets ONLY; Systems is the sole author of formulas/tables/sims. Any number in a Director deliverable is a target, flagged as such.
- Parallel fan-out that shares files silently corrupts work. Mitigation - only fan out across disjoint file trees (Art / sim scripts / new schema); serialize anything touching the same config or the front-end.
- Skipping Gate A and building the client against an unfinished/cheatable endpoint. Mitigation - front-end agents do not start against an endpoint until PHPUnit is green and the live /api/v1 response is shown; hard stop.
- AR/RTL treated as an afterthought (English-first then translated) breaks dense layouts. Mitigation - every presenter task carries AR+EN in scope and verifies both directions at Gate B; schema/API return i18n keys, never hardcoded English.
- AI-tell art slipping through despite the AAA mandate. Mitigation - Art's anti-AI-tell critique pass is a required pre-Gate-B step; presenters verify assets in-context on dark before sign-off.
- Vercel production deploy is irreversible outbound - an agent auto-deploying violates the Approval Gate. Mitigation - stage the deploy, show it, and let Weni press it; agents verify on preview/localhost only.
- Opus cost blowout from running judgment-tier agents on iterative UI edits. Mitigation - opus design passes run once up front; sonnet agents own the high-volume build+verify loop off the finished spec.
